> `subroutine`» и решил строить трекер с нуля. Действующая архитектура —
> [[tracker-architecture-2026-11-16]].
>
> Этот документ **остаётся как разведка**: инвентаризация текущего состояния
> (Teamboard, AngaraChat, pm-global, agent-kanban, subroutine), разбор ADR
> agent-kanban и проверяемые факты о хосте — всё это в силе и используется.

## 0. Короткий вывод (устарело — см. новый документ)

**Новый трекер строить не нужно. Он уже написан, развёрнут, доступен публично — и пуст.**

`subroutine` (`github.com/simonholliday/subroutine`) стоит на этом хосте с 6 сентября,
слушает `127.0.0.1:8471`, отдаёт веб-интерфейс на `https://subroutine.kosov.online/`,
экспортирует 15 MCP-инструментов и имеет ровно ту схему данных, которая нужна для
задач людей и агентов одновременно. Задач в нём **ноль**, MCP-токены для Paseo
выпущены 15 сентября и **не использовались ни разу**.

Прежняя попытка (`agent-kanban`) была удалена 16 октября с собственным ADR
`AngaraConfig/KB/30_decisions/agent-kanban-disabled-2026-10-16.md` — и её выводы
прямо определяют, как строить эту систему, чтобы не повторить судьбу.

Текущий `Teamboard` — не трекер задач, а **слой измерения**: он считает факты из
git. Трекер должен стать **слоем назначений**: кто кому что должен. Это разные
слои, и оба уже существуют — их надо соединить, а не заменять.

**Проблемы применительно к задачам людей:**

| Дефект | Доказательство |
|---|---|
| `owner` — свободный текст, а не идентичность | `human:operator` (19), `Пётр` (35), `az` (29), `legist` (14 — **это агент**), `yaz` (1), `владелец платформы` (4), `upstream getpaseo/paseo` (4), пусто (85) |

| Карточка = ветка git | сам проект признаёт: *«ветка ≠ задача»* (`Teamboard/AGENTS.md:104`) |
| Боты не могут писать | `services/board-project/AGENTS.md:9` — *«прав на записи у тебя нет: доска смонтирована только на чтение»* |

Итог: ответ на вопрос *«какие задачи у Пётра?»* по сегодняшней доске получить
нельзя — владельцы записаны в пяти разных форматах.

### 1.2 AngaraChat / Mattermost — четыре бота, ноль персистентности

Живут: `@comrade`, `@board`, `@triage`, `@legist` (плюс `@pm-reporter`,
`@findings-reporter` из AngaraConfig). Всё поведение — в одном фреймворке
`services/bot-gateway.py` (221 КБ) и `services/bot-mm.py` (54 КБ).

- **Базы данных нет нигде.** Ни SQLite, ни Postgres, ни SQLAlchemy во всём AngaraChat.
  Назначение задачи человеку существует только как текст в чате.
- `mm` — CLI для агентов: `post, read, files, users, reaction, whoami, kb, board,
  tasks, history, profile`. `mm tasks` — **не хранилище**, а фильтр по колонкам
  того же `board.json` (`services/bot-mm.py:736-737, 1053-1086`).
- Делегирование между ботами — текстовый маркер `ЗАДАЧА ДЛЯ @board: …`
  (`services/bot-gateway.py:202-204`) + ожидание ответа *«Принял: …»*.
  Ни состояния, ни истории, ни подтверждения выполнения.
- **Идентичность:** логин Mattermost (латиница) + русское отображаемое имя.
  22 активных пользователя (`users` в Postgres, `deleteat=0`): 12 людей
  (`admin, aleksandr, anastasia, boris, eduard, lada, maksim, maria,
  maria-franz, pavel, petr, zoya`) и 10 ботов (`board, calls, comrade,
  findings-reporter, kb-publisher, legist, pm-reporter, sibres-site, system-bot,
  triage`). Расхождение `petr`/`Пётр` сломано уже сегодня.
- **Различитель «человек / бот» в Mattermost уже есть:** поле `position`
  непустое только у ботов (`board` → «Агент доски задач и проектов`,
  `comrade` → «Инженерный агент», `legist` → «Юридический консультант»),
  у людей оно пустое. Это готовый признак для таблицы `user` в Subroutine:
  `position != ''` ⇒ `is_service_account = 1`.
- Плагинов Mattermost нет — установлен только Calls.

### 1.4 agent-kanban — предыдущая попытка и её разбор

FastAPI + SQLModel + PostgreSQL + React 19 + MCP (11 инструментов).
Развёрнут 13.10 на `kanban.kosov.online`, **удалён 16.10** коммитом `a3e517d`.
ADR `AngaraConfig/KB/30_decisions/agent-kanban-disabled-2026-10-16.md`:

1. **Дублирование git-протокола.** Агенты Paseo уже работают в worktree-ветках
   `feat/<slug>` с auto-commit/auto-merge. Задачи в kanban дублировали то, что
   агенты и так делают: PR как «task», merge как «complete».
2. **Нагрузка на малый VPS.** 13 параллельных агентов с MCP-keep-alive давали
   `Caddy aborting … 502` при любом SIGTERM.
3. **Operator overhead.** Три точки конфигурации (per-project skill + общий skill
   + `mcpServers.kanban`), которые надо держать синхронными.

Вывод ADR: *«Pull-model kanban хорош для команды людей, не для AI-агентов»*.

**Это ключ ко всему.** Прошлый трекер пытался **заменить** git-протокол
координации агентов — и проиграл, потому что координация там уже есть.
Новая система обязана быть **слоем выше git**: git отвечает «как сделано»,
трекер — «кто кому что должен». Никогда не наоборот.

## 2. Диагноз: почему «задачи людей» не работают сегодня

1. **Нет канонического адресата.** Ни в одном слое не существует сущности
   «человек Пётр» с устойчивым id. В доске — свободный текст; в чате — логин
   Mattermost; в трекере — не существует вовсе. Пока адресата нет, невозможно
   ни назначить, ни спросить «мои».
2. **Нет пути записи от агента к трекеру.** `mm` читает доску, но не пишет никуда;
   у `@board` и `@triage` `readWritePaths = []`. Поэтому бот *физически* не может
   завести задачу — только написать о ней текст.
3. **Нет места для срока и приоритета.** Задача человеку почти всегда про
   «когда-то сделать», и без `due_at` она не отличается от заметки.
4. **Агенты и люди в одной строке без типов.** `legist` (14 карточек) стоит рядом
   с `Пётр` (35) в одном поле `owner`. Нет типа «это агент», нет связи
   «агент отвечает перед человеком».

## 3. Решение: Subroutine как система записи

### 3.1 Почему именно он

1. **Схема уже покрывает все четыре требования пользователя** — задачи агентам,
   задачи людям, создание задачи агентом для человека, создание человеком для
   агента. Это не доработка, а штатные поля.
2. **Он уже здесь.** Задеплоен, публичен, с мостом авторизации и мостом к Paseo.
   Нулевые вложения в инфраструктуру.
3. **Он пуст.** Нет миграции данных, нет риска потерять историю.
4. **Он написан под агентов изначально.** В коде инструментов это видно прямо:
   `subroutine_add` — *«Hand it to somebody, by username»*; `subroutine_list` —
   *«Only what is assigned to somebody. 'me' is you.»*; повестка дня специально
   показывает агенту задачи, отданные другим (*«an agent that cannot see the gap
   picks up the wrong thing»*).
5. **Он пережил бытовой сценарий** (задача человеку без агента вообще) — pull-модель
   была проблемой `agent-kanban` именно потому, что тот был агентным. Здесь
   наоборот: человек — основной пользователь, агент — производная сила.
6. **ADR-у agent-kanban не противоречит.** Провал был в дублировании git;
   здесь git-слой остаётся, а трекер живёт над ним.
7. **Меньше движущихся частей.** Урок ADR: *«Tooling overhead должен быть
   обоснован. Каждый новый MCP / daemon / systemd unit — это operating cost»*.
   Новый сервис = новый секрет, новый деплой, новый мониторинг. Subroutine уже
   заплатил за это.

### 3.2 Схема данных: что уже готово

Таблица `task` — 40 колонок, из них решают именно те задачи, которых сейчас нет:

| Требование | Поле |
|---|---|
| Назначение | `assignee_id` |
| Кто назначил (заявитель) | `assigned_by_id` |
| Claim/lease с истечением | `claimed_by_id`, `claimed_at`, `claim_expires_at` |
| Приоритет (две оси) | `importance`, `urgency` |
| Срок и календарь | `due_at`, `due_is_all_day`, `starts_at`, `ends_at`, `reminder_minutes`, `timezone` |
| Отложить | `snoozed_until` |
| Трудоёмкость | `estimate_minutes`, `spent_minutes` |
| Иерархия | `parent_task_id`, `path`, `depth`, `position` |
| Повторения | `recurrence_rule`, `recurrence_anchor`, `occurrence_at` |
| Аудит | `created_by`, `updated_by`, `version`, `deleted_at` |

Остальные таблицы закрывают остальные потребности:

- `user` — `is_service_account` + `responsible_user_id`: **агент = полноправный
  участник, который отвечает перед человеком**. Именно недостающая связь.
- `status` — рабочие статусы: `open, in_progress, blocked, needs_input, done,
  cancelled, superseded`. **`needs_input`** — состояние «агент ждёт человека»,
  ради которого весь заход и затевался.
- `item_type` — не только `task/bug/feature/chore/spike`, но и
  `note/spec/design/decision/finding/dead_end`. Агенты смогут фиксировать
  **решения и тупики** рядом с работой — дословно *«the decisions live beside
  the work»*.
- `comment` — ветки обсуждения (`parent_comment_id`); `event` — журнал с
  `actor_user_id`, `actor_token_id`, `actor_interface`.
- `verification` — `passed`, `commit_sha`, `tree_hash`: **мостик между задачей и
  коммитом в git**. Это то, чего не было ни у Teamboard, ни у agent-kanban.
- `api_token` — `scopes`, `project_scope`, `project_write_scope`, `expires_at`:
  выдача агентам ограниченных учёток.
- `calendar_feed` — персональная ICS-подписка на задачи: **«мои задачи» без
  всякого плагина**.
- `role` — owner / admin / member / contributor / viewer с тонкими правами.

### 3.3 Чего в нём нет и нужно добавить

- **Задача ↔ проект git.** Поле `project.path` есть, но нужен реестр проектов из
  `Teamboard/data/board/registry.json` → 54 проекта в Subroutine.
- **Связь с веткой/commit.** Через `verification` и `metadata`.
- **Импорт из `annotations.json`** — 97 записей суждений станут задачами
  с сохранением `owner`, `why` и `evidence`.

## 4. Интерфейсы

### 4.1 MCP для агентов — уже готов

15 инструментов на `POST http://127.0.0.1:8471/mcp` (streamable HTTP, Bearer `sr_…`):

| Инструмент | Назначение |
|---|---|
| `subroutine_add` | создать задачу, **в т.ч. с `assignee`** |
| `subroutine_list` | список; фильтр `assignee` (в т.ч. `me`) |
| `subroutine_update` | изменить, **в т.ч. `assignee`** — в т.ч. вернуть задачу тому, кто просил |
| `subroutine_claim` | взять в работу |
| `subroutine_done` | закрыть |
| `subroutine_comment` | комментарий |
| `subroutine_show` / `search` / `changes` / `journal` | чтение и история |
| `subroutine_link` / `document` / `project` | связи, документы, проекты |
| `subroutine_whoami` | кто я и что мне можно |
| `subroutine_call_api` | прямой доступ к REST |

Плюс `subroutine mcp` —stdio-вариант для агентов, умеющих только stdio.

**Что нужно сделать:** выпустить токены под каждого агента и вписать их в
конфиги MCP. Токены «Paseo MCP …» от 15.09 уже выпущены — надо лишь
подключить. Это и есть та самая третья точка конфигурации, которая убила
`agent-kanban` — здесь она одна, а не три.

### 4.2 REST API — 76 путей

`/v1/tasks` (+ `claim`, `complete`, `release`, `move`, `skip`, `occurrences`,
`verifications`, `tree`, `governing`, `backlinks`, `links`, `comments`, `events`),
`/v1/projects`, `/v1/documents`, `/v1/comments`, `/v1/agenda`, `/v1/changes`,
`/v1/journal`, `/v1/calendars`, `/v1/login-links`, `/v1/me`, `/v1/meta`,
`/v1/statuses`, `/v1/tags`, `/v1/link-types`, `/v1/admin/backups`,
`/v1/docs/agent` (мануал для агента), `/v1/docs/examples`.

### 4.3 Веб-интерфейс — уже есть, уже публичен

`https://subroutine.kosov.online/` — SPA отдаётся сервисом. Отдельный фронтенд
писать не нужно.

### 4.4 «Мои задачи» без плагина

`subroutine calendar create` выдаёт персональную ICS-ссылку
(`/v1/calendars/{prefix}/{secret}.ics`). Любой календарь показывает задачи
человека. Это работает уже сегодня и закрывает 80% запроса «покажи мои задачи».

### 4.5 Плагин Mattermost

Минимально достаточная форма — **не полноценный Go-плагин**, а слой шлюза:

1. **Slash-команда `/tasks`** — шлюз (или сам бот) вызывает Subroutine от имени
   пользователя (по его маппингу) и печатает его задачи карточкой в тред.
2. **Назначение через чат** — `@коллега назначь Пётру проверить релиз` →
   бот вызывает `subroutine_add --assignee petr` и отвечает номером задачи.
   Это ровно то, чего не хватает сегодня, и это не требует плагина вообще:
   боты уже умеют говорить, нужно лишь дать им инструмент записи.
3. **Plugin как тонкая обёртка** (если нужен UI в Mattermost): встроенный
   iframe на веб-интерфейс Subroutine с передачей сессии — Mattermost 10.11
   поддерживает Apps/iframe. Логику при этом не дублировать.

### 4.6 Плагин Paseo

SDK (`@getpaseo/plugin`) даёт:

- `registerProvider` — агент-провайдер;
- `addHook` — жизненный цикл: `agent.create.before/after`, **`agent.turn.before/after`**,
  `agent.permission.before/after`, `agent.close.after`, `workspace.*`, `worktree.create.*`;
- клиентские компоненты (React Native): `Modal`, `FlatList`, `ScrollView`,
  `TextInput`, `Toast`, `Icon`.

Сценарий: панель «Мои задачи» в Paseo + хук `agent.turn.before`, который
автоматически подставляет агенту его текущую задачу, и `agent.close.after`,
который освобождает claim. Образец структуры — `PaseoPlugins/yeah-provider`
(`paseo-plugin.json` + `index.server.ts` + `server/` + `shared/` + `test/`).

## 5. Границы слоёв: что остаётся в Teamboard

Принцип двух слоёв из `Teamboard/AGENTS.md` переносится целиком и становится
архитектурой всей системы:

```
git (факты: ветки, коммиты, merge, возраст)
        │
        ▼
Teamboard (пересчёт раз в сутки, read-only для ботов)
   board.json  ──►  веб-витрина проектов и инициатив
        │
        │  «кто кому что должен» — суждение
        ▼
Subroutine (задачи, назначения, сроки, статусы, комментарии)
        │
        ├──► MCP  → агенты (Pull/Claim/Complete)
        ├──► ICS  → календарь человека
        ├──► REST → Mattermost, веб, pm-global
        └──► Paseo hooks → авто-claim / авто-release
```

**Правило разграничения:** если состояние выводится из git — оно в Teamboard
(пересчитывается). Если это суждение, договорённость или обязательство
человека — оно в Subroutine (пересматривается). Ни то, ни другое не дублируется.

`@board` (бот доски) продолжает читать `board.json` и **не пишет** в Subroutine:
это измерение. Запись в Subroutine получает `@comrade`/`@triage` — это решения.

## 7. Ошибки, которые нельзя повторить

Из ADR agent-kanban, дословно применимые:

1. **Не дублировать git.** Трекер не заменяет ветку, PR и merge. Он отвечает
   «кто кому что должен», git — «как сделано». Связь — через `verification`.
2. **Не плодить точки конфигурации.** Токен выпускается один раз и раздаётся
   агентам через общий конфиг; вторая точка конфигурации — единый
   `AGENTS.md` бота, третья — MCP-конфиг. Три точки — предел, дальше начинается
   operator overhead.
3. **Не ставить тяжёлое на малый VPS.** Subroutine: SQLite, 200 МБ RAM, один
   процесс. Никаких отдельных Postgres под каждого агента.
4. **Один источник правды на сущность.** Проект — один. Человек — один. Задача —
   одна. Два трекера (Teamboard и Subroutine) живут на разных слоях и не
   делят сущности, только ссылаются друг на друга.
5. **Не писать документацию впрок.** `mattermost-agent-interaction-2026-11-15.md:159`
   описывает «чтение и создание задач на Доске» как сделанное — оно не сделано.
   Документация — код: ADR и README обновляются в том же коммите.

## 8. Риски и открытые вопросы

| Риск | Оценка |
|---|---|
| Subroutine — сторонний проект (v0.1.0.dev0), API может меняться | **Средний.** Зафиксировать ревизию в `flake.lock`, контракт держать через MCP, а не через REST |
| Миграция `annotations.json` наполнит трекер 97 задачами, часть — историческая | **Низкий.** Импортировать с `status=archived` и пометкой источника |
| Агенты начнут плодить дубли задач (как `agent-kanban` дублировал git) | **Средний.** Ограничить: задача создаётся только по явной просьбе; токен агента получает `project_scope`; дедуп по `metadata.source_ref` |
| Неясность: «Назначить на кого угодно» — бот должен проверять, что адресат существует | **Низкий.** `subroutine_add` уже резолвит по username и отвечает ошибкой на неизвестного |
| Mattermost-плагин на Go потребует отдельного цикла сборки и публикации | **Средний.** Начинать с slash-команды и ICS, plugin — отдельным этапом |
| Нужен ли трекер для «задач от людей, не связанных с проектом» | **Решено.** `project.is_inbox = 1` — встроенный Inbox |

**Открытый вопрос для владельца:** считать ли `subroutine` источником правды по
статусам карточек Teamboard, или оставить статусы только у доски? Первый вариант
даёт единую правду и убирает двойной счёт, второй — сохраняет доску
независимой. Рекомендация: **задачи живут в Subroutine, статусы карточек по
веткам остаются в Teamboard**, а связь «задача → ветка → карточка» — явная
ссылка в `metadata`.
