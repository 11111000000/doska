# Бэкенд doska: как он устроен и как должен развиваться

Дата: 19.11.2026.
Статус: **анализ и предложения. Не принятое решение.**

Источник истины по архитектуре — ADR
(`docs/design/doska-architecture-2026-11-16.md`). Этот документ **не правит
ADR** и не создаёт обязательств: всё, что требует решения владельца, собрано
в §7. Правка ADR обнуляет ревью источника у всех 32 claim'ов слоя
доказательств, поэтому предлагаемое не тащится в ADR до решения.

Все числа в документе — результат проверки на живой базе и в рабочем дереве
(как — §9). Не «по плану», а «как есть».

---

## 1. О чём документ

Два вопроса владельца, которые стоит развести:

1. **Как бэкенд устроен сейчас** — слои, границы, что уже работает, что
   лежит в схеме, но не работает, и где на самом деле живёт логика.
2. **Как он должен развиваться** — потому что OCaml выбран недаром: ради
   качественной модели управления задачами, ради вложенных структур, которые
   работают в агентной разработке, и ради того, чтобы человеку было проще
   видеть, кто кому что должен.

Ключевая находка анализа — в §3 и §5:

- use case'ы задач живут **не в сервисном слое, а в HTTP-слое** (`api/tasks.ml`,
  666 строк). Это главный структурный долг: впереди пять интерфейсов
  (REST, MCP, CLI, чат-бот, Paseo), и без общего слоя правила придётся
  копировать в каждый;
- «вложенная структура» сейчас задумана, но **не выражена ни в коде, ни в
  данных**: `parent_id` задан у 0 из 25 задач, `task_link` — пустая таблица с
  нулём строк, кода для неё нет вовсе.

## 2. Что есть на самом деле

### 2.1 Слои и направление зависимостей

Реализовано пять dune-библиотек, зависимости идут строго «снаружи внутрь»:

```
api  →  service  →  db  →  domain  ←  identity
                        ↖─────────────
```

| Слой | Модули | Зависит от | Строк |
|---|---|---|---|
| `domain` | status, actor, task, project, evidence, activity, comment, rules | **ничего** | ~900 |
| `identity` | resolve | domain | 160 |
| `db` | conn, migrate, row, repo_task, repo_actor, repo_actor_alias, repo_project, repo_evidence, repo_activity | domain, identity, lwt, yojson, caqti | ~1800 |
| `service` | resolve, mattermost, import_actors | db, domain, identity | ~390 |
| `api` | errors, params, auth, view, context, tasks, actors, server | db, domain, identity, service, dream | ~1200 |

Правило «домен не знает про БД» обеспечено **структурно**: у `domain` нет ни
одной зависимости, нарушить направление нельзя, не сломав сборку. Это работает
и должно остаться.

Проблема — не в направлении, а в **размере слоя `service`**: в нём три модуля,
и все три — про импорт и разрешение имён. Слой, который по замыслу должен
нести «применение доменных правил к данным базы» (так сказано в комментарии
`src/service/dune`), для задач пуст.

### 2.2 Факт против плана: REST

ADR §6.1 обещает 22 маршрута. Реализовано 11:

| Есть | Нет |
|---|---|
| `GET /tasks`, `POST /tasks`, `GET /tasks/{ref}`, `PATCH /tasks/{ref}` | `GET /tasks/mine` ← **главный запрос** |
| `POST /tasks/{ref}/transition` | `POST /tasks/{ref}/claim`, `POST /tasks/{ref}/release` |
| `POST /tasks/{ref}/assign` | `POST /tasks/{ref}/links` |
| `POST /tasks/{ref}/comment`, `POST /tasks/{ref}/evidence` | `GET/POST /projects`, `POST /actors/{id}/aliases` |
| `GET /activity`, `GET /actors`, `POST /actors/resolve` | `GET/POST/DELETE /credentials` |
| | `GET /overview` |

Отсутствует ровно то, что нужно агентам и визуализациям: взять задачу
(`claim`/`release`), увидеть свои задачи (`/tasks/mine`), увидеть связь
(`/links`), получить сводку (`/overview` — это же вход для D3.js-визуализаций).

### 2.3 Таблицы, которые есть, но не работают

Проверено на живой базе и по коду:

| Таблица / колонка | Строк в БД | Код | Комментарий |
|---|---|---|---|
| `task_link` (7 видов связи) | **0** | **нет ни одной строки** | ADR §3.5: «`blocks` — то, чего нет ни в одной из трёх существующих систем и что нужно реально». Не реализовано |
| `status_rule` | **0** | **нет** | ADR §3.9 «Правила переходов — в базе, машина состояний конфигурируема». Фактически правила — в `src/domain/rules.ml`, таблица пустая |
| `task.parent_id` | **0 из 25** задач | только чтение | `INSERT INTO task` не пишет `parent_id`; эндпоинта нет; дерева нет |
| `task.estimate_minutes`, `spent_minutes` | 0 | нет | учёт времени не делается |
| `credential` | 0 | нет | этап 4 — ожидаемо |
| `notification` (outbox) | 0 | нет | этап 6 — ожидаемо |
| `activity` | 20 | есть | работает, но `interface_` — литерал `"api"` в шести местах |
| `evidence` | 3 | есть | работает |
| `comment` | 2 | есть | работает, `comment.parent_id` — единственная работающая иерархия |

Две строки выше — не «ещё не успели», а **структурное расхождение с ADR**:
ADR обещает конфигурируемую машину состояний и работающие связи, а код
зашивает правила и не знает про связи. `status_rule` — это потенциально два
источника истины об одном и том же.

### 2.4 Где на самом деле живёт логика

Разбор `src/api/tasks.ml` (666 строк) по функциям:

| Что | Где | Строк |
|---|---|---|
| Разбор запроса, фильтры, лимиты | `api/tasks.ml` | ~120 |
| Сбор контекста для домена (автономия, руководитель, наличие evidence) | `api/tasks.ml:decide` | ~30 |
| **Транзакция: смена статуса + запись в журнал** | `api/tasks.ml:apply_transition` | ~35 |
| **Транзакция: назначение + запись в журнал** | `api/tasks.ml:assign` | ~60 |
| Создание, комментарий, доказательство | `api/tasks.ml` | ~200 |
| Ответы HTTP, коды ошибок | `api/tasks.ml` | ~80 |

Домен при этом чист: `Rules.check` получает готовый контекст и возвращает
`Ok`/`Error` с причиной. **Правила проверяются правильно** — но *применяются*
в HTTP-слое, вместе с транзакцией и журналом.

## 3. Главный структурный долг: сервисный слой пуст для задач

Это не стилистическая придирка, а точка, где дорожа становится дороже.

Каждый интерфейс, который появится дальше, должен уметь одно и то же:
перевести задачу по правилам, назначить, взять, отпустить, записать в журнал
с указанием источника. Интерфейсов будет пять:

| Интерфейс | Этап | Как реализуется |
|---|---|---|
| REST | сейчас | `api/tasks.ml` — правила применяются здесь |
| MCP (16 инструментов) | 4 | JSON-RPC поверх своего слоя |
| CLI `tk` | 4 | отдельный бинарник/подкоманда |
| Чат-бот (карточки, кнопки, DM) | 6 | вызовы через тот же REST или свой путь |
| Paseo (хуки `agent.turn.before`, `agent.close.after`) | 8 | события от агента |

Что будет без сервисного слоя:

- либо **правила переходов копируются в пять мест** — и R1 («агент не закрывает
  сам») начнёт расходиться: в REST агент не закроет, а в MCP закроет;
- либо **интерфейсы начинают ходить друг в друга по HTTP** — MCP зовёт REST,
  REST зовёт CLI. Это хрупко и не тестируется так же, как домен.

Что предлагается: `src/service/task.ml` — use case'ы, а `api`, `mcp`, `cli`
становятся тонкими адаптерами над ними.

```ocaml
(* формат, не обязательный дословно *)
val transition :
  Db.Conn.t -> actor:Domain.Actor.t -> ref_:string ->
  to_:Domain.Status.t -> version:int -> note:string option ->
  interface_:Domain.Activity.interface -> Domain_error.t result Lwt.t
```

Что это даёт:

1. **Одно место для правил.** R1 проверяется один раз для всех интерфейсов.
2. **Журнал получает честный `interface_`.** Сейчас `interface_` — литерал
   `"api"` в шести местах; при сервисном слое он приходит аргументом, и в
   журнале видно «это сделал агент через MCP», а не «через api».
3. **Тесты use case'ов — без HTTP.** Сейчас переход проверяется через API
   (`test/api_test.ml`, 21 тест). Use case можно проверять напрямую, без
   сервера, — как сейчас проверяется домен.
4. **Ответственность за транзакцию уходит из HTTP.** Транзакция «сменить
   статус + записать в журнал» — это свойство операции, а не протокола.

Цена: перенос кода. ~200 строк из `api/tasks.ml` в `src/service/task.ml` плюс
изменение вызовов. Перенос механический и проверяемый тестами, которые уже
есть.

> Замечание по слою доказательств: перенос сам по себе обязательств не
> создаёт, но меняет структуру, к которой привязаны claim'ы `api-transition-r1`,
> `api-idempotent-create`, `repo-status-persistence`. После переноса их
> `scope` надо переоформить на новые файлы — это работа для `mathc re-evaluate`
> и новых claim'ов, а не для правки старых.

## 4. Что даёт OCaml — и что из этого не используется

OCaml выбран не «просто так». Ниже — честная карта: что уже работает, что
доступно и не взято, что стоит взять.

| Свойство | Где работает сегодня | Что можно усилить |
|---|---|---|
| **Варианты = закрытые множества** | `Status.t` (8), `Task.kind` (9), `Activity.action` (19), `Actor.kind` (4) | `Activity.interface_` — **строка**, хотя набор известен (`api \| mcp \| cli \| web \| mattermost \| paseo \| import \| system`). Сделать вариантом — компилятор начнёт ловить забытые источники |
| **Исчерпывающий match** | `-w +8 -warn-error +a`: 14 переходов покрыты тестом `domain_test.ml` | то же при добавлении правил и видов связей |
| **`Result` вместо исключений** | домен: `Rules.check : (unit, string) result` | в `db` и `api` ошибка — `string`. «Задача не найдена» и «нет прав» неразличимы на уровне типа. Нужен закрытый тип `Domain_error` |
| **Чистое ядро** | `domain` без зависимостей | сохранить: правило 1 AGENTS.md |
| **Фантомные типы** | **не используются** | `Task.id`, `Actor.id`, `Project.id` — все `string`. Перепутал id задачи и id актёра — компилятор не поймает. Модуль `Domain.Id` с `task_id`/`actor_id`/`project_id` стоит копейки и убирает класс ошибок целиком |
| **GADT** | **не используются** | `Status.t` не несёт данных. `Needs_input` обязан нести **вопрос** (R2), `Blocked` — причину. GADT `Needs_input of question` сделает «переход без вопроса» невозможным на уровне типа. Сейчас — см. §5.4, это дыра |
| **Полиморфные варианты** | **не используются** | реестр правил по виду задачи (`kind`): `module Rule = sig type t val transitions : ... end` — тогда «правила различаются для `bug` и `decision`» выражается типами, а не `if` |
| **Эффекты (OCaml 5)** | **не используются** | ADR §9.1 обещает «эффекты — основа конкурентности». В коде — ручной `Lwt`. Для outbox-доставки и фоновых агрегатов это было бы естественно, но вводить надо с конкретной болью, а не заранее |
| **Иммутабельность и структурное равенство** | `Task.t` — record; `Status.t` сравним | готовая база для «что изменилось» и для чистых тестов редьюсера |
| **Функторы / first-class modules** | **не используются** | для репозитория смысла нет: база одна. Заниматься не нужно — и это нормально, а не упущение |

Вывод: OCaml окупается в домене и в инфраструктуре. **Не окупается он сейчас
там, где нужны данные, а не вычисления** — то есть в трёх конкретных местах
(иерархия, связи, вопрос при `needs_input`). Это важно: если выбранный язык
не используется по назначению, его преимущества остаются незамеченными, а
решение «недаром взяли OCaml» не приносит плода.

## 5. Модель управления задачами: три вида вложенности

«Вложенные структуры управления задачами» — сегодня в проекте это одно
слово, за которым стоят **три разные сущности**. Пока их не развели,
любая правка в этой области будет сбиваться.

### 5.1 Вложенность как дерево — «из чего состоит»

`task.parent_id`: задача — часть другой задачи. Единственный родитель,
дерево, «декомпозиция работы».

- Сейчас: колонка есть, `INSERT INTO task` её не пишет, `0 из 25` задач с
  родителем, эндпоинта нет, дерева не существует.
- Чего не хватает: создание с родителем, выборка поддерева, агрегат по
  поддереву («сколько в этом эпике ещё открыто»), правило «родитель не
  закрыт, пока открыты дети».

### 5.2 Вложенность как граф — «что от чего зависит»

`task_link` (`blocks`, `blocked_by`, `relates_to`, `implements`, `split_from`,
`follows_up`): произвольные связи между задачами.

- Сейчас: таблица пустая, кода нет, `0` строк.
- Отличие от дерева: у задачи может быть несколько связей, граф может быть
  циклическим. Цикл по `blocks` — это «задача A ждёт B, B ждёт A»: такая
  пара не должна молча приниматься, но и не должна ронять запись — человек
  должен увидеть объяснение.
- Это ровно то, чего нет ни в одной из трёх существующих систем, и что ADR
  обещает в §3.5.

### 5.3 Вложенность как контекст — «что берёшь вместе с задачей»

Когда человек или агент берёт задачу, ему нужен не один объект, а срез:
родитель, дети, связи, доказательства, комментарии, требования приёмки.

- Сейчас `GET /tasks/{ref}` отдаёт `task + comments + evidence`. Ни родителя,
  ни детей, ни связей.
- Для агента это значит: чтобы взять задачу, сделать N отдельных запросов.
  Для человека — карточка задачи показывает половину картины.
- Предложение: `GET /tasks/{ref}/context` (или `?context=full`), возвращающий
  один срез. Это же — основа для «Моих задач» и для дерева на вебе.

### 5.4 Вложенность как итерация — «работа → приёмка → отклонение → снова»

Петля агентной разработки: агент взял задачу, отдал на приёмку, её вернули с
замечанием, агент взял снова. Это **цикл**, а не дерево, и сейчас он
выражен только статусом `in_review → in_progress` с причиной в
`activity.summary`.

Отдельная дыра, найденная при разборе: правило R2 требует, чтобы задача в
`needs_input` **хранила вопрос**, а `set_status` сохраняет в строке задачи
только `blocked_reason` — и только для статуса `blocked`:

```ocaml
(* src/db/repo_task.ml:320 *)
let blocked =
  match status with
  | Status.Blocked -> (match note with None -> "blocked_reason" | Some reason -> Conn.quote reason)
  | _ -> "NULL"
```

Для `needs_input` вопрос уходит только в журнал (`activity.summary`) и в
строку задачи **не попадает**. То есть задача, ждущая ответа, не помнит, о
чём её спрашивали. Для агента это ровно то, что ломает работу: «жду ответа»
без адресата и без вопроса.

### 5.5 Как они соотносятся

```
        ┌─ parent ────────┐        ┌─ link ─────────┐
задача ─┤                 ├─ задача ┤                ├─ задача
        └─ children ──────┘        └─ blocked_by ───┘
        ┌─ context ───────┐        ┌─ iteration ─────┐
        └─ evidence,      │        └─ attempt,       │
           comments,      │           rejection,     │
           acceptance     │           history        │
```

Четыре разных механизма, четыре разные таблицы (частично отсутствующие). Смешивать
их в один `parent_id` — значит получить структуру, которая выражает только
дерево и ломается на первом же «эта задача блокирует две другие из трёх».

**Как это превращается в «проще и понятнее»:**

| Роль | Сейчас | Стало |
|---|---|---|
| Человек | «Мои задачи» — плоский список; карточка — половина данных | дерево работ и карточка со срезом: родитель, дети, связи, история |
| Агент | `my_tasks` + `get_task` + угадать, что ещё спросить | `whoami` + `my_tasks` + `get_task(context)` — три вызова, полный контекст |
| Руководитель | «что застряло» — отдельный отчёт | иерархия показывает, где застрял **эпик**, а не одна задача |

## 6. Как должен развиваться бэкенд

### 6.1 Ближайший порядок работ

Порядок — по соотношению «стоимость × отдача», а не по номеру этапа из ADR.
Этапы 3–10 в ADR — это внешние интеграции; внутри них нужен фундамент, иначе
каждая интеграция будет тащить свою копию правил.

| # | Что | Почему сейчас | Что даёт |
|---|---|---|---|
| 1 | **Сервисный слой задач** (`src/service/task.ml`) | use case'ы в `api/tasks.ml`; сервисный слой пуст | один набор правил для пяти интерфейсов; честный `interface_` в журнале |
| 2 | **`GET /tasks/mine`** | «главный запрос» ADR §6.1 отсутствует | это и есть продукт: человек открывает трекер и видит свои задачи |
| 3 | **claim / release** | агент не может взять задачу | «взять» — ядро агентного конвейера; без него R1 не на чем проверять |
| 4 | **Иерархия и связи** (`parent_id` в API, `task_link`) | 0 строк, 0 кода | вложенность; `blocks` — то, чего нет ни в одной из трёх систем |
| 5 | **`GET /overview`** | обещан в §6.1, нет | вход для визуализаций (D4, D3.js) |
| 6 | **Вопрос при `needs_input`** (миграция) | R2 не выполняется | агент и человек видят, о чём спрашивали |

Пункты 1–3 — до этапа 4. Пункт 4 можно начать раньше: он не зависит от
интерфейсов, только от схемы (которая уже готова).

Пункт 1 сделан 20.11.2026 (D5): use case'ы задач живут в `src/service/task.ml`,
REST стал тонким адаптером, интерфейс действия — тип `Interface.t`, отказ —
значение `Service.Failure`. Что именно сделано и что осталось открытым — ADR
§11 («Факт на 20.11.2026: сервисный слой»).

Пункт 2 сделан 20.11.2026: `GET /tasks/mine` — открытые задачи исполнителя по
всем проектам, порядок по срочности (просроченные первыми), курсорная
пагинация по полному ключу порядка. Что именно сделано и что осталось
открытым — ADR §11 («Факт на 20.11.2026: главный запрос»).

Пункты 3–6 — следующие по очереди. Пункт 3 (`claim` / `release`) — ядро
агентного конвейера и то, на чём дальше проверяется R1.

### 6.2 Что добавляется по этапам

| Этап | Внешнее | Что должно появиться внутри бэкенда |
|---|---|---|
| 3. Миграция | импорт registry/annotations/epics | идемпотентный импорт как use case сервисного слоя, а не скрипт; сейчас импорт есть только для акторов |
| 4. Агенты | MCP, 16 инструментов, bearer-токены | `credential` (таблица есть, кода нет); `auth` вместо заголовка `X-Doska-Actor`; `can_assign` — правило назначения переезжает из `api/tasks.ml:may_assign` в домен |
| 5. Люди | веб, ICS | `overview`; представления для визуализаций (D3.js) |
| 6. Чат | slash-команды, карточки, DM | `notification` (outbox): таблица есть, кода нет; доставка — отдельный воркер, а не часть запроса |
| 7. План дня | pm-global пишет в трекер | дедлайны как первоклассная величина: `due_at` есть, а «сегодня/неделя» живут в ad-hoc фильтре |
| 8. Paseo | панель, хуки | освобождение claim'а по событию агента — значит claim должен быть **состоянием**, а не записью в журнале |
| 9. Чистка | удаление `subroutine` | миграция данных, если что-то переносится |
| 10. Плагин MM | Go-плагин | только адаптер: всё остальное уже в общем сервисном слое |

### 6.3 Что должно остаться в ядре, а что — уйти на периферию

Принцип, который стоит зафиксировать: **ядро — это модель обязательств,
периферия — способы говорить с человеком и агентом**.

| Ядро (`domain` + `service`) | Периферия (`api`, `mcp`, `cli`, чат, Paseo, веб) |
|---|---|
| правила переходов и приёмки | HTTP-коды, JSON, карточки Mattermost, кнопки |
| модель задачи, связей, иерархии | форматирование под интерфейс |
| назначение, claim, права | аутентификация конкретного протокола (bearer, заголовок) |
| доменные события | доставка уведомлений, outbox-воркер |
| проекции для чтения (сводки) | визуализации (D3.js) |

Сейчас граница проходит не там: часть правил в домене, часть применения — в
`api`, доставка уведомлений не спроектирована вовсе. §6.1 пункт 1 и есть
исправление этой границы.

## 7. Решения, которые нужны от владельца

Каждое — с вариантами и рекомендацией. До решения соответствующий пункт
`docs/design/doska-architecture-2026-11-16.md` не правится.

| # | Вопрос | Варианты | Рекомендация |
|---|---|---|---|
| **D5** | Где живут use case'ы задач | (A) `src/service/task.ml`, API/MCP/CLI — адаптеры; (B) оставить в `api`, вынести общий модуль; (C) API зовёт API | **A** — сервисный слой уже объявлен в `src/service/dune`, но пуст; это ровно его назначение |
| **D6** | Правила переходов: код или база | (A) код, таблицу `status_rule` удалить; (B) таблица — источник истины, код её интерпретирует; (C) таблица — только подсказки для интерфейса | **A** — типы дают проверку целостности, а правила должны быть частью кода, который компилируется. Два источника истины — уже факт (§2.3) |
| **D7** | Иерархия и связи | (A) `parent_id` (дерево) + `task_link` (граф), оба в API; (B) отдельная сущность «работа/эпик»; (C) только `task_link` | **A** + новое правило: **родитель не закрывается, пока открыты дети** |
| **D8** | Что делает `needs_input` | (A) `task.question` + миграция, вопрос обязателен; (B) оставить в журнале | **A** — R2 прямо требует, чтобы задача хранила вопрос; сейчас не хранит |
| **D9** | Как хранить итерации приёмки | (A) `task.attempt` + `task.rejection_reason`; (B) считать из журнала; (C) отдельная таблица `task_iteration` | **A** — дёшево, видно сразу, достаточно для петли «работа → приёмка → отклонение» |
| **D10** | Фантомные типы идентификаторов | (A) `module Domain.Id` с `task_id`/`actor_id`/`project_id`; (B) оставить `string` | **A** — убирает целый класс ошибок, стоит почти ноль |
| **D11** | Тип ошибок в `db`/`api` | (A) закрытые типы `Domain_error`; (B) строки | **A** — «ошибка — данные» (правило 4) означает, что данные должны быть типизированы |

Отдельно, не требуя решения, но требующих внимания:

- **«Правило назначения переедет в домен на этапе 2»** (ADR §11 и
  `src/api/tasks.ml:483`) — расхождение: этап 2 — это идентичность, а
  `can_assign` приходит с `credential` на этапе 4. Формулировку надо поправить
  отдельной правкой ADR.
- **Право назначать** (`may_assign`) сейчас живёт в `api` — при переносе
  use case'ов в сервисный слой оно уезжает вместе с ними, но проверку прав
  (`credential.can_assign`, `scopes`) надо писать заново под этап 4.

## 8. Риски

| Риск | Средняя | Что делаем |
|---|---|---|
| Каждая правка ADR обнуляет ревью источника у 32 claim'ов | высокая | цикл ревью проходили уже дважды; поэтому предложения живут здесь, а не в ADR |
| «Слишком умный» домен: GADT, эффекты, first-class modules | средняя | вводить только под конкретную боль; не начинать с GADT-статусов, если не болит |
| Дрейф двух источников правил (код и `status_rule`) | уже есть | D6 |
| Массовый рефакторинг `api/tasks.ml` перед этапом 4 | средняя | делать узко: переносить use case'ы без изменения поведения, тесты уже есть |
| Новые ограничения БД (дерево, циклы) ломают существующие данные | низкая | данных мало: 25 задач, связей 0 |

## 9. Чем проверялось

Все утверждения — из этих проверок, а не из чтения плана:

```sh
# структура и зависимости
ls src/*/dune; grep -rn "library" src/*/dune
grep -rn "task_link\|status_rule\|estimate_minutes\|spent_minutes\|credential\|notification" src/

# живая база
psql "postgresql:///doska" -tAc "select 'tasks', count(*) from task union all ..."

psql "postgresql:///doska" -tAc "select status, count(*), count(*) filter (where blocked_reason is not null) from task group by status;"

# код

grep -rn "interface_:" src/

```

`proven`, `uncovered: 0 file(s)`.
