# Журнал решений

Append-only: запись не переписывается, новое решение — новая строка. Вопрос
«почему так» должен иметь ответ в репозитории, а не в памяти участника.

Кто принял:

- **владелец** — прямое решение человека;
- **владелец (указание)** — решение, оформленное по прямому поручению человека
  (например, «доделать» от 18.11.2026);
- **реализация** — техническое решение в рамках уже принятого; оно не меняет
  обязательств владельца и не требует его ревью.

| **«Мои» — это исполнитель, и он приходит из заголовка актора** | `:me` — идентификатор актора из `X-Doska-Actor`; клиент не подставляет логин в тело запроса | реализация | Иначе «мои задачи» означали бы «задачи, которые я назвал», и главный запрос перестал бы быть главным. Требование уже было в SQL ADR §6.1 (`t.assignee_id = :me`) — реализация следует ему, а не меняет его | ADR §6.1 |
| **Открытость задачи — три признака сразу** | `deleted_at IS NULL` AND `completed_at IS NULL` AND `status NOT IN ('done','cancelled')` | реализация | Один признак пропустил бы закрытые задачи: задача, принятая переходом в `done`, и задача, удалённая в мягкую корзину, выглядели бы как открытые | `src/db/repo_task.ml` |
| **Порядок — по срочности, четырьмя корзинами** | 0 — просрочено, 1 — срок в ближайшие сутки, 2 — срок позже, 3 — срока нет; внутри корзины — срок, приоритет, давность, идентификатор | реализация | Просроченное — первое, что человек должен увидеть. Идентификатор в конце ключа нужен для полного порядка: без него равные строки переставлялись бы между страницами | ADR §6.1 |
| **`COALESCE(due_at, 'infinity')` вместо `NULLS LAST`** | Ключ порядка сравнивается как кортеж; пустой срок заменяется на `infinity` | реализация | В сравнении кортежей Postgres даёт для NULL «неизвестно», а не «больше»: с чистым `due_at` задачи без срока нельзя было бы расставить между собой, и курсорная пагинация по ключу порядка была бы некорректной. Порядок тот же, сравнение — рабочее | ADR §6.1, `src/db/repo_task.ml` |
| **Курсор — идентификатор последней задачи страницы** | Неверный курсор (не uuid) игнорируется; курсор на несуществующую задачу даёт пустую страницу | реализация | Ошибка в курсоре — не ошибка запроса: клиент с битым курсором получает первую страницу, а не 400. Поведение совпадает с `GET /tasks` | ADR §6.1 |
| **Маршрут `/tasks/mine` раньше `/tasks/:ref`** | Порядок регистрации маршрутов в `src/api/server.ml` | реализация | `Dream` проверяет маршруты по порядку списка: иначе параметризованный маршрут перехватил бы `mine`, и запрос ушёл бы в чтение задачи по референсу | `src/api/server.ml` |
| **Пересмотр источника для всех 43 claim'ов (правка ADR от 20.11.2026)** | `mathc map` → `mathc re-evaluate` → `mathc review-source` от имени владельца → `mathc run` | владелец (указание) | Правка ADR обнуляет ревью источника у всех claim'ов. Человеческий review не присваивает себе агент; основание — прямое поручение владельца от 20.11.2026 («Ну и да приступаю к реализации») | `spec.json`, поле `source.review` |

## 21.11.2026 — решения по заявке и отпуску (`claim` / `release`)

Третий срез по §6.1: агент берёт задачу в работу (`POST /tasks/:ref/claim`) и
возвращает её в пул (`POST /tasks/:ref/release`).

| Решение | Суть | Кто | Почему | Где зафиксировано |
|---|---|---|---|---|
| **Отпустить может исполнитель-агент или любой человек** | Новое доменное право `Assignee_or_human` для перехода `in_progress → todo`; общий `/transition` для этого перехода сузился тем же правилом | реализация | ADR §4.1 обещал «agent (release), human», а код разрешал всем (`Anyone`): правило, записанное дважды, разошлось с архитектурой. Источник права теперь один — домен, а REST, MCP и CLI прочитают одно и то же | ADR §4.1, §6.1, `src/domain/rules.ml` |
| **Заявка не отменяет назначение** | Исполнитель меняется только если задача была свободна (`assignee_id IS NULL`) | реализация | Назначение — это обязательство, а не подпись «времянно сдал на тебя». Заявка, отменяющая чужое назначение, отдавала бы задачу молча, и прежний исполнитель узнал бы об этом из чужого журнала | ADR §6.1, `src/service/task.ml` |
| **Отпуск всегда возвращает в пул** | `assignee := NULL` и статус `todo` — при любом отпуске | реализация | Иначе задача формально свободна, но в «моих» остаётся у того, кто отпустил, и никто её не возьмёт: пул без возврата — это не пул | ADR §6.1, `src/db/repo_task.ml` |
| **Версия обязательна в теле** | `{version, reason?}`: без версии — 400, с устаревшей — 409 | реализация | Оптимистичная блокировка здесь и есть механизм взаимного исключения двух претендентов. Без неё заявка была бы гонкой, а не блокировкой: второй претендент считал бы задачу свободной | ADR §6.1, `src/api/tasks.ml` |
| **Неверное состояние — 409, нарушение правила — 403** | Отказ по состоянию (заявка не из `todo`) и отказ по правилу (чужой агент) — разные коды | реализация | Неверное состояние лечится повторным чтением, нарушение правила — нет. Один код на оба случая прятал бы разные причины отказа за одним числом | ADR §6.1, `src/service/failure.ml` |
| **Одна функция репозитория на статус и исполнителя** | `set_status_and_assignee` с троичным `~assignee` (`None` — не трогать, `Some None` — снять, `Some (Some id)` — назначить); `set_status` — обёртка | реализация | Смена статуса и смена исполнителя — одна транзакция. Два вызова с разными наборами полей разъедутся при первом же изменении формы записи | `src/db/repo_task.ml` |
| **Миграция не понадобилась** | Значения `claimed` и `released` уже были в перечислении `activity_action` с первого перечисления | реализация | Применённый файл миграции менять нельзя (§9.2), а менять было нечего: значения в перечислении были изначально | `migrations/001_init.sql` |
| **Пересмотр источника для всех 43 claim'ов (правка ADR от 21.11.2026)** | `mathc map` → `mathc re-evaluate` → `mathc review-source` от имени владельца → `mathc run` | владелец (указание) | Правка ADR обнуляет ревью источника у всех claim'ов. Человеческий review не присваивает себе агент; основание — прямое поручение владельца от 21.11.2026 | `spec.json`, поле `source.review` |

## 21.11.2026 — решения по иерархии и связям (родитель и связи)

Четвёртый срез по §6.1: задача делится на части (`parent_id`) и связывается с
другой задачей (`task_link`).

| Решение | Суть | Кто | Почему | Где зафиксировано |
|---|---|---|---|---|
| **Два новых модуля: `src/domain/link.ml` и `src/db/repo_link.ml`** | Вид связи — доменный тип с разбором имени; доступ к связям — отдельный репозиторий | реализация | Вид связи — это то, что должны понимать домен и правила (кольцо блокировок), а не только API. Если бы вид связи остался строкой в SQL, правило «кольцо запрещено» проверялось бы в слое, который про него ничего не знает | ADR §6.1, `src/domain/link.ml`, `src/db/repo_link.ml` |
| **Связь — отдельная сущность, версии задачи у неё нет** | Тело — `{to, kind}`; снятие — `DELETE /tasks/:ref/links/{link_id}` | реализация | Связь не меняет задачу: смена состава связей не ломает блокировку карточки. Требовать версию там, где нет блокировки, — значит заставлять клиента присылать число, которое ничего не защищает | ADR §6.1, `src/api/tasks.ml` |
| **Повтор связи — 409, в том числе записанный с другой стороны** | Проверка в сервисе: `from`/`to` местами — та же связь | реализация | Иначе «A блокирует B» и «B блокирует A» жили бы в базе как две записи, и вопрос «кто кого блокирует» имел бы два ответа | ADR §6.1, `src/service/task.ml` |
| **Кольцо блокировок — 400 с цепочкой в сообщении** | Проверка обходом графа; в сообщении — цепочка вида «A → B → C → A» | реализация | «Кто мешает» превращается в «все мешают всем», и работа встаёт. Цепочка нужна отправителю, чтобы увидеть, где кольцо началось, и не гадать | ADR §6.1, `src/service/task.ml` |
| **Снять чужую связь — 404, а не 403** | Связь снимается, только если её `from_id` или `to_id` совпадает с задачей, из которой снимают | реализация | Клиент обратился не к тому ресурсу: связь не принадлежит этой задаче. 403 говорил бы «запрещено», будто право есть, а его нет | ADR §6.1, `src/service/task.ml` |
| **Родитель — дерево, версия обязательна** | `POST /tasks/:ref/parent` с телом `{parent, version}`; `parent` — ссылка родителя или `null` | реализация | Смена родителя меняет задачу, а значит ломает её оптимистичную блокировку. Родителя можно задать и при создании задачи — тогда дерево строится сразу, а не двумя запросами | ADR §6.1, `src/api/tasks.ml`, `src/service/task.ml` |
| **Кольцо по родителю запрещено** | Проверка вверх по цепочке `parent_id`, а не на один шаг | реализация | Родителем нельзя назначить задачу, которая уже является потомком этой: дерево замкнулось бы в кольцо. Проверка на один шаг поймала бы только прямое кольцо | ADR §6.1, `src/service/task.ml` |
| **«Родителя не закрывают, пока открыты дети» — доменное правило** | `Rules.check_parent_closed`; число открытых детей считает сервис и передаёт через `Rules.context.open_children` | реализация | Это правило переходов, а не деталь REST: оно должно одинаково работать из REST, MCP и CLI. Домен при этом про базу не знает (AGENTS.md, правило 1) — число детей приходит числом | ADR §6.1, `src/domain/rules.ml`, `src/service/task.ml` |
| **Циклы проверяет сервис** | И кольцо блокировок, и кольцо по родителю — обход графа по данным | реализация | Проверка цикла — это запрос данных, а не правило предметной области. Помещать её в домен означало бы либо отдать домену знание о базе, либо смоделировать граф в его типах | ADR §6.1, `src/service/task.ml` |
| **Миграция не понадобилась** | `task.parent_id` и `task_link` были в `001_init.sql`; `linked` и `unlinked` — в `activity_action` | реализация | Применённый файл миграции менять нельзя (§9.2), а менять было нечего: схема была готова с первого дня | `migrations/001_init.sql` |
| **Пересмотр источника для всех 50 claim'ов (правка ADR от 21.11.2026)** | `mathc map` → `mathc re-evaluate` → `mathc review-source` от имени владельца → `mathc run` | владелец (указание) | Правка ADR обнуляет ревью источника у всех claim'ов. Человеческий review не присваивает себе агент; основание — прямое поручение владельца от 21.11.2026 | `spec.json`, поле `source.review` |
