# Ведение doska: с чего продолжить

Назначение документа: [ADR](design/doska-architecture-2026-11-16.md) отвечает на
вопрос «что делаем и почему архитектура такая». Этот — на вопрос «где мы
находимся, как ведём разработку и на что смотреть в первую очередь». Он живой:
вместе с кодом меняются разделы «где мы сейчас» и «что дальше».

- Архитектура, принципы P1–P8, DDL, машина состояний, интерфейсы, этапы 0–10,
  решения D1–D3 — [ADR](design/doska-architecture-2026-11-16.md).
- Что, кем и почему решено — [журнал решений](decision-log.md).
- Правила агента: код, база, слой доказательств — [AGENTS.md](../AGENTS.md).
- Откуда берём данные для импорта и что переиспользуем, а что нет —
  [разведка по estate](research/estate-research-2026-11-16.md).

Что в коде:

- `src/domain` — статусы, переходы, правила R1–R3, задачи, актёры, проекты, виды
  связей. Не знает про БД и HTTP: это обеспечено раздельными библиотеками dune.
- `src/identity` — нормализация имён и резолвер алиасов. Ни базы, ни HTTP.
- `src/db` — caqti: подключение, свой мигратор, репозитории (task, actor,
  actor_alias, project, evidence, activity, link, overview).
- `src/service` — слой между базой и доменом: use case'ы задач
  (`Service.Task`), отказ как значение (`Service.Failure`), резолвер против БД
  (`Service.Resolve`), клиент Mattermost (`Service.Mattermost`), импорт
  актёров (`Service.Import_actors`), сводка (`Service.Overview`). Домен сюда
  не смотрит, HTTP — тоже.
- `src/api` — dream: REST `/api/v1`, `/healthz`, `/version`.
- `src/version` — имя и версия.
- `src/bin` — cmdliner: `doska serve | migrate | health | version | import`.

Схема (11 доменных таблиц + `schema_version`): `actor`, `actor_alias`,
`project`, `task`, `task_link`, `evidence`, `comment`, `activity`, `credential`,
`notification`, `status_rule`. У актора ещё `source` и `source_ref` —
ключ внешнего объекта (`migrations/003_actor_source.sql`).

REST. Всё под `/api/v1` требует заголовок актора:

```
GET   /api/v1/tasks                 POST   /api/v1/tasks
GET   /api/v1/tasks/mine            ← главный запрос: мои открытые задачи
GET   /api/v1/credentials           POST   /api/v1/credentials → токен один раз
DELETE/api/v1/credentials/:id       ← отзыв; bearer вытесняет X-Doska-Actor
GET   /api/v1/tasks/:ref            PATCH  /api/v1/tasks/:ref
POST  /api/v1/tasks/:ref/transition POST   /api/v1/tasks/:ref/assign
POST  /api/v1/tasks/:ref/claim      POST   /api/v1/tasks/:ref/release
POST  /api/v1/tasks/:ref/comment    POST   /api/v1/tasks/:ref/evidence
POST  /api/v1/tasks/:ref/links      DELETE /api/v1/tasks/:ref/links/:link_id
POST  /api/v1/tasks/:ref/parent
GET   /api/v1/overview              ← сводка: где застряло и кто перегружен
GET   /api/v1/activity              GET    /api/v1/actors
POST  /api/v1/actors/resolve        {raw, namespace?} → actor | placeholder
```

Заявка и отпуск требуют версию в теле: `{version, reason?}`. Без версии — 400,
с устаревшей — 409.

Сводка: `GET /api/v1/overview?stuck_days=N&limit=M`. Оба параметра необязательны
(по умолчанию 7 суток и 20 записей), оба возвращаются в ответе. Вне диапазона
(`stuck_days` меньше суток, `limit` вне 1…200) — 400, как и неразобранное
значение параметра.

Связь — отдельная сущность, версии у неё нет: тело `{to, kind}`, где `kind` —
одно из семи значений `link_kind`. Родитель меняется телом `{parent, version}`
(`parent` — ссылка родителя или `null`), версия обязательна и здесь.

Вне области с актором: `GET /`, `/version`, `/healthz`, `/api/v1/healthz`.

Идентификация на этапе 1 **временная**: заголовок `X-Doska-Actor` с логином
актора, администраторы — `DOSKA_ADMIN_HANDLES`. Это не аутентификация: заголовок
подделывается тривиально, поэтому сервер должен слушать только доверенную сеть.
Токены, `credential` и хеширование — этап 4 (ADR §11).

Импорт из Mattermost: `doska import --source mattermost`. Переменные
`DOSKA_MATTERMOST_URL` (по умолчанию `http://127.0.0.1:8065`) и
`DOSKA_MATTERMOST_TOKEN` — секрет приходит только из окружения. Импорт
идемпотентен: ключ актёра — пара `(source, source_ref)`.

## 2. Как поднять с нуля

Требования: Nix с флейками, PostgreSQL 17 с `citext` и `pg_trgm` (расширения
создаёт миграция).

```sh
nix develop                       # dev-окружение: dune, ocaml, mathc
nix develop -c bash -c 'dune build --root . && dune runtest --root .'
nix develop -c bash -c 'mathc --root . run'
nix build .#doska --no-link       # пакет
nix path-info .#doska             # путь к бинарю в store
```

База:

```sh
createdb doska
export DOSKA_DATABASE_URL="postgresql:///doska"      # или TCP-URI, см. §6
nix develop -c bash -c 'dune exec --root . src/bin/doska.exe -- migrate --db-url "$DOSKA_DATABASE_URL" --migrations-dir migrations'
nix develop -c bash -c 'dune exec --root . src/bin/doska.exe -- health --db-url "$DOSKA_DATABASE_URL"'
```

**Умолчания у CLI и у тестов разные.** `doska` без `--db-url` берёт
`DOSKA_DATABASE_URL`, а если её нет — `postgresql://127.0.0.1/doska`: TCP без
пароля. Локально это не сработает, поэтому `--db-url` лучше задавать явно.
Тесты (`test/support.ml`) при отсутствии переменной берут unix-сокет
`postgresql:///doska`. Явный `--db-url` перекрывает переменную окружения — это
проверено, а не предположено.

Тесты живые: `repo_test` и `api_test` работают против настоящей БД и сами
применяют миграции. Без базы они падают — это правильное поведение, а не
поломка (claim `test-harness-needs-db`). `mathc run` тоже требует живой БД:
claim'ы о миграторе и репозиториях работают против неё.

## 3. Как вести изменения

- Ветка `etap-1`, изменения — через PR. **Пуш в `main` — только по явной
  просьбе человека.**
- Агент — исполнитель. Принята та работа, что независимо перепроверена: сборка,
  тесты, `mathc run`, а для изменений в поведении — живая проверка (например,
  поднятый сервер и запрос по HTTP).
- Человеческие решения метода (`waive`, `record`, `review-source`,
  `authorize`) фиксирует владелец. Агент не присваивает себе человеческий
  review и не создаёт waiver без разрешения.
- Чужие репозитории (AngaraChat, Teamboard, AngaraConfig, Mattermost) не
  трогаются без прямого указания.
- Секреты — только из окружения. Токены Mattermost лежат в `/etc/secrets/…` и
  недоступны агенту: если этап требует их, это запрос к владельцу, а не повод
  искать обходной путь.
- `subroutine` удаляется на этапе 9 и не раньше (ADR §11).

Перед PR проверь себя:

```sh
nix develop -c bash -c 'dune build --root . && dune runtest --root . --force'
nix develop -c bash -c 'mathc --root . run'
```

Оба — зелёные, и оба вывода приложены к сообщению: `verdict` и `uncovered`
вместе, никогда по отдельности. Если менялось поведение — добавь живую проверку
(поднятый сервер и запрос), потому что тест и `mathc` не показывают, что
изменилось то, что задумано. Если трогался ADR — он устарел, и пересмотр
источника делает человек (§4).

Внешний дашборд прогресса живёт в соседнем репозитории AngaraChat
(`paseo-progress`). Это вспомогательное: состояние проекта обязано читаться из
этого репозитория, а не из дашборда.

## 4. Слой доказательств на практике

Метод описан в [AGENTS.md](../AGENTS.md), здесь — операционные детали, которые
не видны из правил и стоили времени при внедрении.

**Коды возврата verifier'а.** `0` — проверка прошла; `1` — отказ проверки
(именно его обязан давать отрицательный control); `2` — «неопределённо»;
`123`, `124`, `125`, `139` — сбой инфраструктуры, а не отказ проверки;
`126`, `127` — не запущено. Если verifier падает с `123`, mathc считает это
аварией, control не засчитывается, и claim остаётся `inconclusive`. В OCaml
ошибка разбора командной строки транслировалась в `123` — поэтому проверки
обязаны завершаться явным `exit 1` на всех путях отказа.

**Control обязан ронять verifier кодом ровно 1.** `2` даёт `inconclusive`,
`123` — `infrastructure-error`.

**Control не восстанавливает файлы.** mathc выполняет control в изолированной
копии и сравнивает digest области до и после. Восстанавливающий control даёт
`control_reach: nothing` → claim становится `inconclusive`, а не `holds`.

**Control не ломает сборку** — он ломает поведение. Иначе падение verifier'а
ничего не доказывает: он и так был бы красным.

**mathc снимает изолированную копию дерева.** Если в этот момент кто-то правит
файлы, копия получается битой и mathc падает на ровном месте. Если дерево
меняется во время прогона — гонять на снимке:

```sh
D=$(mktemp -d) && tar -cf - --exclude=./_build . | tar -xf - -C "$D" && cd "$D"
```

**Verifier не зависит от способа подключения к базе.** URL берётся из
`DOSKA_DATABASE_URL`, заведомо отсутствующая база — тот же сервер с другим
именем. Жёстко зашитый unix-сокет работает на машине разработчика и молча ломает
проверку в CI, где postgres доступен по TCP (правило 8 в [AGENTS.md](../AGENTS.md)).

**Правка ADR обнуляет ревью источника.** После правки ADR — `mathc map`:
claim'ы с этим источником покажут `source changed` и станут `outdated`. Дальше
`mathc re-evaluate` → `mathc review-source ID --by Peter --reason "..."` (это
человеческое решение) → `mathc run`. Правило касается и текста, и таблиц: ADR
не должен дублировать живой перечень claim'ов, он на него ссылается.

**Перед `mathc run` — снять состояние dune-daemon.** mathc копирует дерево
вместе с `_build` для каждого отрицательного control'а; живой daemon в `_build`
наследуется копией, и сборка в ней висит на чужой блокировке. Помогает
`scripts/clean-dune-state.sh` (снимает `_build/.dune`, `_build/.db`,
`_build/.digest-db`, `_build/.lock`).

**Зелёный вердикт относится только к объявленным claim'ам.** `uncovered`
сообщается вместе с вердиктом, никогда по отдельности.

**Зелёный — это факт прогона, а не свойство проекта.** Заявление о нём
пишется с датой последнего `mathc run`. После любых правок `spec.json`, ADR
или кода прежнее заявление считать ложным: `mathc map` покажет `outdated`
или `never-checked`, и нужен новый прогон. Устаревший след — не «почти
зелёный», а отсутствие доказательства.

**Мета-проверка** `test/check_controls.sh` (сам объявлен claim'ом): каждый
control меняет ровно один файл, применим к текущим исходникам и объявлен
control'ом ровно одного claim'а. Прогоняется в составе `mathc run`.

## 5. База, фикстуры и параллельные прогоны

Фикстуры тестов делят общие префиксы: актёры `api-`, `repo-`, `idn-`, `svc-` и
`ov-`, проекты `APIMAIN`, `APIAUTO`, `REPOMAIN`, `REPOPAGE`, `SVCMAIN`, `OVMAIN`,
`OVEMPTY`, источники задач `test-api`, `test-repo`, `test-identity`,
`test-service` и `test-overview`.

Параллельные прогоны одного теста задевали фикстуры друг друга: уборка одного
удаляла строки, только что созданные другим, и тест падал на ровном месте.
Решено advisory lock'ами в `test/support.ml`: `4711` — миграции, `4712` —
`api_test`, `4713` — `repo_test`, `4714` — `identity_db_test`, `4715` —
`service_task_test`, `4716` — `service_overview_test`. Блокировка берётся на
уровне сессии и снимается с соединением, то есть при выходе из процесса:
зависшего прогона она не оставляет.

`service_overview_test` живёт в отдельной базе `doska_overview_test`: в URL из
`DOSKA_DATABASE_URL` меняется только имя базы, способ подключения не зашит.
Причина — фикстуры сводки считают открытые задачи, и на общей базе они
сталкивались бы с фикстурами тестов API.

Уборка фикстур выполняется **в начале** прогона, а не в конце: `Alcotest.run`
завершает процесс, код после него не выполняется. Поэтому после последнего
прогона в рабочей базе остаются его строки (`test-api`, `test-repo`,
`test-identity`, актёры `api-`/`repo-`/`idn-`, проекты `API*`/`REPO*`) — их
уберёт следующий прогон. Если база должна остаться чистой, удали их вручную.

`identity_db_test` живёт в собственных пространствах имён (`idn-*`) и на
префиксе логинов `idn-`: живые данные Mattermost он не трогает и не спорит с
ними за имена.

## 6. CI

`.github/workflows/ci.yml`, двенадцать шагов: сборка и тесты → сборка пакета →
смоук миграции (применение, повторное применение, health) → проверка схемы →
установка mathc с закреплённой контрольной суммой → **`mathc run` как
обязательный гейт**, а не отчёт.

- Postgres в CI — только по TCP: `postgresql://postgres:postgres@127.0.0.1:5432/doska`.
  Локально обычно unix-сокет. Отсюда правило «проверка работает там, где её
  запускают» (§4).
- Проверка пакета (`checkPhase`) гоняет в герметичной песочнице nix только тесты
  без БД — домен и идентичность: PostgreSQL в песочнице нет, а тесты
  репозиториев и API без живой базы честно падают. Тесты с БД гоняют CI
  (отдельный сервис postgres) и локальный `dune runtest`.
- Шаг «Install mathc» изредка падает с `Failed to allocate signal stack for
  domain 0` — это раннер, не код. Лечится перезапуском прогона.

Контракт работы субагентов (один на все волны):

- все работают в одном дереве репозитория; git-коммиты делает только
  координатор. Граница механическая: pre-commit hook (`.githooks`)
  отклоняет коммит без `DOSKA_COORDINATOR=1`; hooksPath включается на
  клоне — `git config core.hooksPath .githooks`;
- брифы дробятся на порции ≈1 часа; после каждой порции агент пишет
  короткий статус — падение по rate limit не должно съедать сделанное;
  незаконченную работу дочитывает координатор, а не новый субагент;
- ADR, `spec.json` и `AGENTS.md` правит только координатор; claim'ы (verifier,
  falsifier, control) агенты предлагают, координатор оформляет `mathc add`;
- не больше двух тяжёлых проверок параллельно; `mathc run` запускает только
  координатор и при низком CPU pressure;
- каждая волна мержится в `etap-2` после зелёных гейтов; пуш — только по слову
  владельца.

Ориентир по этапу 3 (параллельная дорожка), в порядке:

1. **Импорт проектов** из `Teamboard/data/board/registry.json` (58 на
   25.11.2026; число — факт чтения файла, не константа): `key` — id,
   `repo_path`, `asset_class`.
2. **Импорт суждений** из `Teamboard/data/board/annotations.json` (97) в задачи:
   `owner` → актёр через резолвер, неразрешённое имя → заглушка.
3. **Импорт инициатив** из `epics.json` (20/75) — в проекты.
4. **Проверка повторного импорта**: тот же запуск не должен плодить ни задач,
   ни алиасов.

Данные для импорта берутся не из этого репозитория, а из estate: реестр
проектов — `Teamboard/data/board/registry.json` (58 на 25.11.2026), суждения —
`Teamboard/data/board/annotations.json` (97), инициативы — `epics.json`
(20/75).

## 8. Открытые вопросы владельцу

1. **Один workspace или персональные пространства** (ADR §13) — не блокирует
