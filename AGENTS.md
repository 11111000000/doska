# AGENTS.md — doska

Трекер обязательств для людей и агентов. OCaml-сервер, общий TypeScript-слой
фронтенда (`frontend/packages/core`, D4-R) и веб на веб-компонентах (D3.js),
PostgreSQL.

Документация и обсуждения — на русском. Код, комментарии, идентификаторы и
коммиты — по-русски или по-английски, как в соседних файлах; главное —
единообразие внутри файла.

## Что здесь главное

Трекер отвечает на вопрос «кто кому что должен». Он **не** пересчитывает
git-факты, **не** дублирует доску Teamboard и **не** хранит переписку из
Mattermost. Наблюдение о внешнем мире — это ссылка (`evidence`), а не копия.

> **Факт пересчитывается владельцем факта. Суждение живёт в трекере.**

Ветка, PR и коммит — приложенное доказательство внутри задачи. Задача —
обязательство. Если правка превращает ветку в «задачу», это неверно.

## Команды

```sh
nix develop                                   # dev-оболочка
dune build --root .
dune runtest --root .
nix build .#doska --no-link                   # пакет
nix path-info .#doska

doska migrate --migrations-dir migrations
doska health
doska serve --port 8500
```

Dev-оболочка считает `OCAMLPATH` вручную (findlib-hook работает только в
сборках) — это сделано в `flake.nix`, руками ничего дописывать не надо.

Проверка перед коммитом — обе команды должны быть зелёными:

```sh
nix develop -c bash -c 'dune build --root . && dune runtest --root .'
```

## Правила кода

1. **Домен не знает про БД.** `src/domain` и `src/identity` не импортируют
   `db`, `api` и не знают про HTTP. Это обеспечено раздельными библиотеками
   dune, а не только соглашением.
2. **`Result` вместо исключений.** «Переход запрещён» — это
   `Error (Forbidden_by_rules ...)`, а не исключение. Домен не бросает.
3. **Предупреждения — ошибки.** В корневом `dune` включено
   `-w +8 -warn-error +a`: неполный `match` по статусам не собирается, и
   любое другое предупреждение, включённое профилем dune (например, unused
   open), тоже. Это зафиксированное правило проекта, а не дефолт тулинга, —
   проверь его, если сборка ругается на предупреждение. Добавил статус →
   обнови все места, где статус разбирается.
4. **Ошибки — данные.** Промиссы в `db` и `api` — `Lwt_result.t`. Связка
   внутри них — явный `Lwt.bind` (встроенный в stdlib `>>=` работает с
   обычными значениями и перехватывает промиссы).
5. **Тайна — только в окружении.** Секреты читаются из переменных
   (`DOSKA_DATABASE_URL`), в код и в SQL не попадают.
6. **Комментарий объясняет «почему», не «что».** Если код делает очевидное
   действие, комментарий не нужен.

## Правила базы данных

- Миграции — идемпотентные SQL-файлы в `migrations/`, имя задаёт порядок.
- Один файл применяется **целиком в одной транзакции**; отметка — в таблице
  `schema_version` вместе с контрольной суммой файла.
- Файл **не правится после применения**: следующая правка — новый файл.
- Мигратор сам делит файл на выражения: драйвер работает по extended protocol
  и не допускает несколько операторов в одном запросе. Разбор учитывает
  строковые литералы, `--`/`/* */` комментарии и `$$`-блоки.
- Схема не содержит имени проекта. Референс задачи — `DSK-<номер>`.

## Границы этапов

`subroutine` удаляется **на этапе 9 и не раньше**: пока трекер пуст, он не мешает,
а его удаление ломает мост авторизации и bridge с Paseo раньше, чем замена
готова. Не начинай выпиливание `subroutine` без прямого указания.

Плагин Mattermost на Go — волна 4, по решению D3-R он идёт **после** бот-пута
(собственный webhook `/hooks/mattermost`: команды в чате, карточки с кнопками,
DM), а не раньше замены.

## Где смотреть решение

`docs/design/doska-architecture-2026-11-16.md` — архитектура целиком: границы,
принципы, DDL, машина состояний (14 переходов, правила R1–R3), идентичность,
интерфейсы (REST, 16 MCP-инструментов, CLI, веб, realtime), этапы 0–10, риски,
решения D1–D3.

`docs/development-guide.md` — ведение проекта: где мы находимся, как поднять
с нуля, как работать со слоем доказательств на практике, что делать на этапе 2,
какие вопросы открыты. Читай его первым, если продолжаешь с нуля.

`docs/decision-log.md` — что, кем и почему решено. Отвечает на вопрос «почему
так», не дублируя ADR.

Ключевые решения владельца:

- **D1 (приёмка).** Агент не закрывает свою задачу сам — закрывает заявитель
  или руководитель. Для доверенных проектов — режим `project.autonomy='auto'`.
  Правило R1 в `src/domain/rules.ml`.
- **D2 (единица работы).** Задача = обязательство. Ветка / PR / коммит —
  `evidence` внутри неё.
- **D3 (Mattermost).** Сначала бот-путь, Go-плагин — поздним этапом 10.

## Границы репозитория

- Чужие изменения в соседних репозиториях (AngaraChat, Teamboard,
  AngaraConfig) не трогаются без прямого указания.
- Пуш в `main` — только по явной просьбе человека.
- Неполный `match` «потом поправлю» — не оставляется: предупреждение 8 включено
  как ошибка именно для этого.

## Слой доказательств

Принятая архитектура — источник обязательств, `mathc` — слой, который
связывает каждое обязательство с проверяемым доказательством. Правила:

1. **Новое обязательство — новый claim.** Если правка вводит свойство,
   которое должно быть истинным (правило приёмки, идемпотентность миграции,
   запрет на смену применённого файла), это оформляется claim'ом со своим
   verifier'ом, falsifier'ом и **control'ом**.
2. **Claim без control'а — не claim.** Control обязан менять предмет и
   заставлять verifier падать. Если verifier падает и без control'а, он не
   проверяет ничего: падение из-за синтаксиса или из-за отсутствия базы —
   не доказательство. Control'ы лежат в `test/break/` и правят предмет
   точечно, ровно одно место.
3. **Зелёный — только по объявленным claim'ам.** `mathc run` печатает
   `uncovered`: файлы вне покрытия остаются непроверенными. Зелёный verdict
   и список `uncovered` сообщаются вместе, никогда по отдельности.
4. **След не редактируется.** `.math/` — evidence, а не содержимое: он
   генерируется прогонами и не переносится в репозиторий. Не ослабляй
   verifier и не меняй control ради зелёного результата.
5. **Человеческие решения — за человеком.** `waive`, `record`,
   `review-source`, `authorize` фиксируют решения владельца. Агент не
   присваивает себе человеческий review и не создаёт waiver без разрешения.
6. **Архитектура меняется — claim'ы стареют.** После правки
   `docs/design/doska-architecture-2026-11-16.md` прогони `mathc map`: claim'ы
   с этим источником покажут `source changed` и станут `outdated`. Пересмотр
   источника делает человек (`mathc review-source ID --by Peter --reason ...`),
   после чего нужен новый `mathc run`.
7. **Блок `math-coding:begin/end` в этом файле принадлежит `mathc install`.**
   Руками его не правь; свои правила пиши выше.
8. **Проверка обязана работать там, где её запускают.** Не зашивай способ
   подключения к базе: бери URL из `DOSKA_DATABASE_URL` и меняй только имя
   базы. Жёстко зашитый unix-сокет работает на машине разработчика и молча
   ломает проверку в CI, где postgres доступен по TCP: control перестаёт
   ломать verifier, и claim остаётся `inconclusive`.

Перед тем как объявить этап закрытым:

```sh
nix develop -c bash -c 'dune build --root . && dune runtest --root .'
nix develop -c bash -c 'mathc --root . run'
```

`mathc run` требует `DOSKA_DATABASE_URL` — claim'ы о миграторе работают против
живого PostgreSQL.
