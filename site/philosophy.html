философия

Суждение живёт в трекере. Факт — у своего владельца.

Каждый принцип doska выведен из наблюдаемого дефекта, а не из вкуса: в чате всё обсуждено, в git всё закоммичено — а ответ на вопрос «кто кому что должен» приходится собирать руками. Это и есть дефект, который трекер устраняет.

главное правило

Факт пересчитывается владельцем факта. Суждение живёт в трекере. Наблюдение — ссылка, а не копия.

Это правило наследует принцип, который уже доказал работоспособность в этом хозяйстве: «факт пересчитывается, суждение пересматривается». Трекер добавляет к нему третий слой — ссылку на факт. Git-факт нельзя скопировать в трекер: копия протухнет при первом rebase. Нельзя и пересчитывать его самому — это работа git. Остаётся ровно одно честное поведение: помнить ссылку и не претендовать на чужое.

принципы

П1–П8: каждый принцип — из дефекта

П1

Назначение — ссылка на актора, а не строка

Дефект: owner — свободный текст: «Пётр», «az», «human:operator», пусто — 85 карточек. Вопрос «задачи Петра» не отвечаем. → assignee_id — внешний ключ, свободного текста в поле назначения нет физически.

П2

Люди и агенты — одна сущность

Дефект: агент стоял рядом с человеком в одном поле — неразличимы. → Единая таблица actor с признаком kind и связью supervisor_id: агент отвечает перед человеком.

П3

Агент не закрывает свою задачу

Дефект: «закрыто» перестаёт быть проверяемым, если закрывающий совпадает с исполнителем. → Машина состояний с правилами переходов, проверяемыми на сервере.

П4

Каждое изменение оставляет след

Дефект: «кто и откуда плодит задачи» — неразрешимый вопрос. → Append-only журнал activity с интерфейсом: api · mcp · cli · web · mattermost · paseo · import · system.

П5

Git — источник ссылок, а не состояния

Дефект: трекер-пересчёт git’а молча расходится с реальностью. → Таблица evidence: sha, ветка, PR, файл, URL. Трекер их не проверяет — он помнит, что было приложено.

П6

У агента ровно одна точка входа

Дефект: три точки конфигурации убили предыдущий трекер агентов. → Один credentials-реестр + один MCP-конфиг + один AGENTS.md бота. Меньше — нельзя.

П7

Польза в первый же день

Дефект: трекер, в который надо «сначала перенести всё», не будет adopted. → Импорт существующих данных + ICS-календарь + команды в чате, где человек и так находится.

П8

Нет трекера для трекера

Дефект: сущности, размазанные между системами, врут по отдельности. → Каждая сущность живёт в одном месте; Teamboard и doska ссылаются друг на друга, а не делят «задачу».

урок, вбитый в конструкцию

Провал предшественника и эпистемическая честность

история

Почему не kanban для агентов

Предшественник — agent-kanban — умер не от недостатка функций, а от конструкции: три точки конфигурации, и агенты уже работали в worktree-ветках со своим протоколом координации. Трекер, который заменяет git-протокол, конкурирует с ним и проигрывает. Поэтому doska живёт над git-протоколом, а не вместо него.

честность

Метрика «закрыто» должна быть проверяемой

Если агент может закрыть свою задачу сам, «закрыто» значит «исполнитель так решил» — это не проверка. Правило R1 переносит эпистемическую честность из отчётов в рабочий процесс: агент доходит до in_review и просит приёмки; закрывает человек. Сервер не позволяет иначе — независимо от настроения агента.

не-цели

Чего здесь не будет

  • Не заменять git-протокол координации агентов.
    Агенты уже работают в ветках с auto-commit и auto-merge. Трекер — над этим, а не вместо.
  • Не быть ещё одним местом, куда надо сходить.
    Каждая функция доступна там, где человек или агент уже находится: чат, календарь, терминал, Paseo.
  • Не быть общим чатом задач.
    Обсуждение — комментарии внутри задачи; разговор остаётся в Mattermost.
  • Не тянуть больше, чем нужно.
    Postgres на том же инстансе, один процесс API + один воркер outbox. Никакого Redis и брокеров.
